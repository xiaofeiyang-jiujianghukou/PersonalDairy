# 三端协作设计方案(详细)

> 目标形态:**电脑端(桌面)/ 服务端 / 手机端** 三方协作的"微信式"私人日记。
> 电脑端像微信一样:用**手机扫码**登录电脑端,登录即**同步全部数据、增量更新**。
> 服务端负责**加密数据中转 + AI 通信**(可上云);同一网络下则**点对点互传**。

---

## 一、核心原则(不变)

1. **数据私有存本地**:每台设备各自存完整一份,日记内容只在你的设备上(不交给内容服务器单方持有)。
2. **多端对等**:电脑、手机(任意终端)是**对等**的;没有任何一台是"所有人的总库"。
3. **同步 = 设备↔设备 / 设备↔服务端中转**:只是"数据如何到达对方"不同,合并规则一致。
4. **增量 + 加密**:只传改动;传输/中转全程 **端到端加密**,任何中转方只能看到密文(或协同 AI 时仅接触你授权的内容)。
5. **零负担**:扫码即登录、即同步,像微信那样"不用配地址、不用管"。

---

## 二、三端角色

| 端 | 角色 | 数据 | 主要职责 |
|---|---|---|---|
| **手机端** | 记录端(主写) | 本机 IndexedDB 完整一份 | 写日记、图片、触发同步、**扫码授权/登录新设备**、看小结 |
| **电脑端** | **Linux 桌面应用**(打开即"登录页",像微信) | 本机 SQLite 完整一份 | 打开 → **登录(手机扫码 / 用户名密码)**→ 进入日记;受信任设备,读写/回看 |
| **服务端** | **中继 + AI + 身份鉴权**(可选、可上云) | **不存内容**(仅加密转发 / AI 任务时临时接触授权数据) | ① 不同网络下**加密中转**;② **AI 通信**;③ **账号身份与登录鉴权** |

> 关键词:**服务端不持有你的日记内容**。它要么只转发密文,要么在你**显式发起 AI 任务**时接收那一天/那个月的授权数据并加密返回;它**只持有"账号/身份"**(用户名、密码哈希、会话、设备授权),用于登录鉴权。

---

## 三、两种同步模式(自动选择)

### 模式 A:同一网络 = **点对点直传**(最优)
- 手机与电脑(或两台终端)在同一局域网,`./start.sh` 在电脑上即一个可被发现的"对等端点"。
- 手机**扫码配对**后,直接把增量(密文)发给对方端点;/ 对方也直接回传。**不经过任何中间服务器**。

### 模式 B:不同网络 = **服务端中转**
- 有一台**常在中继**(你的电脑 / 家中 NAS / 云 VPS)持有"加密转发"能力。
- 设备们把增量**加密**后交给服务端,服务端**只转发密文**、不通读;另一台设备稍后拉取。"先落桶、再取走",从而**两端不需要同时在线**。

> 模式选择:能直连就 A(更快、完全不经过服务端);否则 B(经你自己的中继服务,密文)。

---

## 四、鉴权 + 微信式登录与授权

### 4.1 鉴权范围(本期)
> **先只做「用户名 + 密码」登录**;手机号登录、微信登录**预留**(接口/字段留好,本次不实现)。

- **账号模型**:服务端持有一个**账号**(用户名、密码哈希、会话 token、已授权设备列表)。它只用于"登录/身份",**不存你的日记内容**。
- **登录方式(本期)**:
  1. **用户名 + 密码**(电脑端/手机端通用) → 服务端校验 → 发**会话 token**;
  2. **手机扫码登录**(微信式,见下)。
- **预留(不做)**:手机号短信 / 微信 OAuth / 第三方登录 —— 预留字段与接口位。

### 4.2 电脑端 = Linux 桌面应用(打开即登录页)
- 电脑端不再是"`start.sh` 起网页",而是一个 **Linux 桌面应用**(可用 Tauri/Electron 打包)。
- **打开 → 登录页**:
  - 显示一个**待登录二维码**(一次性、临时);
  - 或提供**用户名/密码**输入框。
  - 登录成功后进入日记界面。

### 4.3 微信式扫码登录(目标体验)
1. **手机是"账户主人"**:手机端登录了你的账号,持有"主身份 / 设备组密钥"。
2. **电脑开 App → 显示待授权二维码**(临时、一次性、含会话意图)。
3. **手机扫码** → 手机上确认"登录/授权这台设备" → 通过**端到端加密信道**把:
   - 该设备的**会话/设备密钥**授予电脑;
   - 用既有设备**端到端地把全部数据**同步过去(或该设备拉)。
4. **登录即同步、增量**:登录后进入你的"设备组",增量拉取全部历史,之后不再重复全量。

> 体验 = 微信式:电脑打开 → 手机扫一下码 → 自动登录并全量同步 → 之后增量。**无需重复输入用户名密码**(第一次也可用用户名密码,或作为备用)。

## 五、数据模型(本地优先 + 同步引擎)——已就绪

- 每条日记 `id` 为 **UUID**(全局唯一);`device_id` 记录最后写入设备;`updated_at` 用于 **LWW**;`deleted_at` 为**删除墓碑**(同步传播删除,不物理删)。
- **增量同步**:各端记"同步水位(引子标记)",只传水位之后的改动;若水位被将来时间戳污染则自愈为一次全量。
- **图片内容寻址**:图片以 SHA-256 为 id(`diary-img:<hash>`),条目只存短引用;同步按哈希补图,已拥有不重传。
- **合并**:同一 id 取 `updated_at` 较新者;墓碑优先传播删除。
- 以上已在 `packages/shared`(`sync.ts` / `images.ts`)+ 服务端 `db.ts` 落地。

---

## 六、加密与安全

- **端到端加密**:同步负载 AES-256-GCM,密钥由"扫码配对/授权"在设备间建立;中转/中继只见密文。
- **设备密钥**:每台设备一个密钥(或共享设备组密钥),经安全信道授予新设备;不落任何第三方。
- **密钥永不入库**:密钥在电脑端(如 `synckey`/本机)与手机(密钥库);`.env` 里的 AI 密钥只在服务端。
- **可选**:后续加"字段级加密 / 口令派生密钥"(你记得口令即可换机恢复,无第三方)。

---

## 七、服务端职责与部署

### 两种服务形态(二选一或都做)
1. **中继(转发密文)**:只做"设备间加密数据的暂存/转发";不做 AI。可极简、低资源。
2. **AI 通信端**:客户端把**授权的那部分(某月/某日)日记(可端到端加密)**发给它,它调用 AI 模型(`/api/summarize`),返回加密结果。**它不因此持有你的全部日记。**

### 部署位置(任选)
| 选项 | 说明 | 适合 |
|---|---|---|
| **你家里电脑** | 既当你的终端,也顺带当中继/AI(现状) | 最省事,在家即可用 |
| **家中 NAS / 常开服务器** | 专用于中继 + AI,不关机 | 想"随时可同步/AI" |
| **云服务器(VPS/轻量)** | 独立部署服务端(带 AI 密钥),无公网 IP 难题 | 想"多端随时、无需家里开机" |

### 上云要点
- 服务端只需配置 AI 密钥即可跑"AI 通信";中继模式无需任何数据。
- 设备可配置"服务端地址"(如生成的二维码指向服务端,或全局配置),**数据仍本地、传输加密**。
- HTTPS 可选(公网建议配);同网走 http(已允许明文)。

## 八、端到端流程(示例)

1. 你每天在**手机**写日记(本地存)。
2. 回到家,**手机与家里电脑同网** → 自动**点对点增量加密同步**(模式 A),两端一致。
3. 你在**电脑**上回看、偶尔改一改;也自动增量和**手机**一致。
4. 你**出差(手机流量)**:写日记存手机(本地);等服务端/或下次同网时增量上去。
5. 你**换新电脑**:新电脑开 App → 显示待授权码 → **手机扫码授权** → 用**端到端方式**从手机/服务端**增量拉取全部历史**。
6. **AI 月小结**:手机/电脑任一发起 → 服务端(`/api/summarize`,含图可视觉)加密生成返回;本地缓存。

## 十、与现有实现的关系

- **已完成的基础(可复用)**:
  - 本地优先 + 设备各自存(电脑 SQLite / 手机 IndexedDB);
  - 点对点同步(扫码配对)+ **增量 + LWW + 墓碑 + 图片内容寻址**;
  - **端到端加密**(shared `syncCrypto`)+ 同步水位;
  - 服务端 `/api/sync`(双向增量)+ `/api/summarize`(自包含可上云的 AI 接口);
  - 手机端可安装 APK、块式编辑器、日历/搜索、自动同步、一键启停。
- **待扩展(本方案)**:
  - **账号鉴权(用户名密码,预留手机号/微信)+ 电脑端 Linux 桌面应用(打开即登录页)**;
  - **微信式扫码登录**(扫码授权新设备、登录即全量同步、之后增量);
  - 服务端**中继**形态(不同网络密文中转,先落桶再取走);
  - **服务端地址配置**与公网部署(HTTPS/安全);
  - 手机↔手机、导出/导入搬迁;
  - AI 陪伴对话(同样服务端可部署)。

## 十一、分期落地路线(建议顺序)

| 阶段 | 内容 | 说明 |
|---|---|---|
| **P0(现状)** | 本地私有 + 点对点增量加密同步 + 服务端 AI 小结 + 手机 APK | 已具备 |
| **P1** | **账号鉴权(用户名密码)+ 电脑端 Linux 桌面应用(打开即登录页)+ 微信式扫码登录** | 本期目标:电脑=桌面App,登录后全量同步、之后增量 |

| **P4** | **AI 陪伴对话**(公共能力、服务端可部署)+ 手机↔手机 | 补齐愿景 |

## 十二、关键取舍

- **为什么不把数据存服务端**:违背"数据只在你自己设备"初衷;服务端只做中转(见密文)与授权 AI(见片段)。
- **为什么要微信式扫码**:避免输地址/密码,体验与微信一致,同时靠"你在场的手机"做授权,安全性靠设备在侧。
- **中转 vs 点对点**:能直连就直连(更快、完全不经过服务端);否则经自己的中转服务,数据仍加密。
- **AI 的代价**:AI 功能需要把"授权的那部分日记"交给模型;这是功能换取便利,可在设置里显式开关。
